# Listing filters and sidebar chat

`app-starter/public/listing-filter-schema.js` exports the canonical `FILTER_SCHEMA` (`acres.listing-filters/1`). Its 19 required properties cover borough, area, both price bounds, maximum $/BSF, both lot bounds, zoning, FAR headroom, deal tiers, property types, risk and landmark exclusions, sorting, map following, and four cost overrides. It supplies defaults, enum options, labels, units, bounds and validation for browser state and the research service. Percentages use fractions. Null costs use the saved baseline; empty selection arrays include all options. Observed map bounds belong to the map and are not editable coordinates in the model contract.

The normal authenticated conversation run accepts `listingFilters: {prompt, snapshot}` alongside its existing `message` and idempotency `id`. `snapshot` is `{schema, revision, values, baselineCosts, map?}`; `values` contains every property, and `baselineCosts` supplies the effective saved costs for relative edits. The queued event persists this input so restart and event replay preserve it. Filter results are stored in the ordinary assistant message as `filterContext: true` and `filterUpdate: {base, values}`.

A reused request ID must keep the conversation, message and complete optional filter context unchanged. Adding or removing that context, or changing its prompt, revision, values, baseline costs or captured map context, returns HTTP 409. Use a fresh ID for a new request. JSON object member order and the stored JSON representation of numeric zero do not affect an exact retry. An authorized collaborator may acknowledge the same existing request; its original sender and execution remain unchanged.

Jev receives the complete current snapshot as JSON. It first selects the request mode and any blanket clear/reset instruction from preparsed source spans. Code distinguishes clearing constraints from restoring defaults. A dependent call selects per-field actions against that known starting state; independent value decisions then receive the entire schema and snapshot together. Text extraction selects source boundaries in subsequent calls. Arbitrary numeric literals and simple relative calculations are evaluated in code. Jev never generates unchecked JSON. Every answer must select a supplied option, and the complete final state must validate before it is published. Unsupported amounts, invalid ranges, timeouts and invalid responses fail without changing controls. The integration follows the [TypeSafe typed Choice contract](https://docs.typesafe.ai/api).

Filter-only requests skip the research agent and integration initialization. Research-only prompts preserve controls and follow the normal research workflow. A combined request supplies the final filter state to research and returns it with the research result. Legacy partial `dealSearch` results cannot replace a modern schema-based state.

Numeric values retain a leading decimal point: `$.5m` means $500,000, `.75` FAR means 0.75, and `.5 percent` means 0.5%. Comma-separated values retain their signs, while hyphenated numeric ranges keep positive endpoints. Invalid negative prices fail schema validation without changing the snapshot.

The browser applies all values together and refreshes the page and pins. Search changes clear the old bounds and reframe the matching pins, as manual filters do; cost-only changes retain the current map scope. Undo restores the reader's full state from before an uninterrupted group of chat changes, including map following, cost previews and unapplied cost text. Manual input, selection or cost Preview starts a new restore point. Invalid or deferred replies retain an existing Undo action. Revisions, values and baseline costs must still match the submitted snapshot; manual edits or a map move leave the reply unapplied and expose an explicit Apply chat filters button. After a baseline write finishes, deferred Apply feedback reflects that it is available again. Cost changes are previews. Save as my baseline persists them independently; Undo changes the preview and does not reverse a saved baseline.

The service reads `TYPESAFE_API_KEY` from its secrets, or the existing `ACRES_KNOWLEDGE_CONFIG` file (default `/etc/acres-research/knowledge.json`). The key never reaches the browser. `LISTING_JEV_MODEL` defaults to `jev-latest`. The research installer copies the canonical browser schema into its service directory, following the existing plan-intake deployment pattern.

Cost drafts remain separate from the applied query state. After the first successful response, snapshots carry the four effective cost values; later filter, page, pin and detail requests keep that snapshot even if saved-default metadata changes. A null cost in a chat update resolves to the saved baseline at application time, subject to the usual stale-snapshot check. Validation returns a normalized copy: hard cost uses whole dollars; soft/carry fractions and the gross factor use three decimal places, matching the owning model. The schema declares that output precision with `multipleOf`.

The form preserves typed text and mounted inputs during background refreshes. Save and Reset are serialized, newer typing stays unapplied, and acknowledgements do not relabel old results. Completed list and detail responses retain their own cost context for labels and underwriting, including fractional percentages in the shared underwriting formatter. Initial pins wait for the first cost snapshot; open details refresh when costs are applied. Undo restores prior applied values and drafts, while retaining typing made after the chat update. Filter panels reposition when status content grows as well as when the viewport changes.

Saved filter answers expose **Use these filters** in the ordinary conversation, including after reload or opening history. This explicit action opens Home and replaces the complete filter state without calling Jev again. Costs use the saved response values, or its recorded baseline for null overrides. If an older snapshot has no recorded baseline for a null cost, that cost follows the current profile. Baseline metadata stays attached to the current profile. The action validates the saved schema before applying, clears unapplied filter and cost drafts, and starts a new Undo group that restores the prior applied filters and cost drafts. Historical messages never change the map merely because they are opened.

Manual and chat refinements keep an active reader-selected map area. Changing borough or ZIP/neighborhood deliberately clears that area and fits the new location. Undo restores the previous search area and viewport, including when the map is hidden; a later reader move takes precedence over the earlier area. While the list follows the map, the pins request carries the same bounds as the page, so a reader move reloads both; without bounds the pins cover every match. A late pin response is superseded by the pins for a newer area and cannot refit a map the reader has since moved, even with map-following disabled. Clearing the map area invalidates pending filter snapshots. Manually toggling map-following ends the previous chat Undo group.

MapLibre automatic resize tracking is disabled; a container observer and the existing explicit resize entry point tag layout resizing as programmatic. Opening chat, changing result content or resizing the viewport therefore does not become a new reader-selected map area. This uses MapLibre's [trackResize option](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/MapOptions/#trackresize) and the same event-data flag already used by result fitting and listing reveal.

Research-only and combined runs forward the full immutable snapshot to research, including the resulting filter values and saved cost baselines. Optional read-only `map: {revision, bounds, viewport}` records the page query area and visible viewport at the same five-decimal precision as the HTTP query. Reader map moves invalidate pending updates even when following is off; layout changes do not. Enabling following uses the captured viewport, while changing borough or area clears the old bounds. Legacy snapshots without map metadata remain valid.

Native deal searches inherit page criteria, map scope, ranking, the 250-ZFA opportunity threshold and all four resolved cost assumptions. Explicit arguments override individual values, including zero and false. `useCurrentFilters: false` clears inherited search constraints and map bounds for an independent comparison, while keeping captured costs. Null costs select the captured baseline; unavailable assumptions require an explicit value rather than silently using house costs. The page HTTP query and research share one canonical mapping. Listing-scoped empty results do not start a market sync unless explicitly requested and permitted. Research reads do not mutate controls.

Every native deal search also records its effective criteria, resolved costs, returned count, result limit and retrieval time in a source snapshot, including empty results. `dealSearches` retains these independent captures in source order across research lanes and persists them with the assistant message. The answer's Listing searches disclosures show each scope and assumptions with direct access to its search evidence. Copied answers include the same context. Legacy answers without captures stay unchanged; these read-only disclosures never apply filters or change the map.

Routing asks two independent typed questions in one Jev request: whether the prompt affirmatively requests a page-control edit, and whether it asks for substantive analysis. Code combines the answers into the existing research, filters or both modes. Keeping every control unchanged prevents the field-edit stage; a comparison, hypothetical scenario or explanation still runs research. Keeping other controls does not cancel an explicitly named edit. A keep-only request returns a full unchanged snapshot without querying individual fields. Every request still carries the canonical schema and full current snapshot. Quoted commands and scenario-only costs remain analysis parameters unless the user asks to apply them to the page.

The analysis judgment checks every clause, rather than selecting the message's main command. A comparison-only area or cost still requests analysis when another clause updates a different page filter. Only explicitly requested page values change; parameters limited to the comparison remain research inputs.
## Numbered pins and area matching

Each pin carries `rank`, its position in the ranked match list the cards page through (unlocated matches keep their numbers; their pins are absent). Cards show the same number, the map draws it on the pin and the popup leads with it. Clicking a pin whose card is on another page turns the list to that page and marks the card, so Back to results lands on it.

Area and zoning text match literally: `%`, `_` and `\` are escaped in every `LIKE`. A ZIP+4 searches its five-digit ZIP. ZIP codes mixed with other words are refused with an error naming the word (`listingAreaZips`), in the page, in links and saved searches, in chat updates and in the store. With the Unpriced tier selected, listings without an ask pass the price and $/BSF bounds; priced listings still meet them.

Chat amounts that cannot plausibly mean their field are refused for an explicit value instead of applied: a bare price or project cost under $10,000 ("under 2"), $/BSF under $10, lot or buildable area under 100 SF, or FAR headroom over 50. A scale word (k, m, million) makes a small amount explicit.

## Saved searches

The filter drawer keeps named searches per account. **Save search** stores the applied filters with their costs frozen (as a share link does), the map area while following and the condo hard cost, without a chat message. Selecting a saved name applies all of it again as one change Undo reverses; each can be renamed or deleted. Research stores them in the market store (`market_saved_searches`) under names unique to the account, validated by the same contract; the web server forwards only `name` and `search` to `GET/POST /market-store/saved-searches` and `PATCH/DELETE /market-store/saved-searches/:id`.

Each recorded listing search under an answer also offers **Use these filters**. `listingSearchValues` inverts `listingSearchFilters`, so the page sends the identical query, map area and costs; criteria the page cannot set (another listing status, a different unused-area floor, an any-use $/BSF cap, a ZIP and an area together, a store-only order) are named in the receipt.

## Sharing a search

Home's **Share search** control produces a root URL with a `search` query parameter containing the canonical schema ID, all 19 applied values and the active map bounds. It resolves nullable costs against the captured baseline before serialization, including zero fractions, so opening the link uses those explicit preview costs independently of the recipient's saved baseline. Typed, unapplied form drafts are excluded.

The link omits conversation, project and account identity, revisions, unrelated query parameters and fragments. It grants no application access. Opening it validates the complete values and geographic bounds before the first page/pin requests, restores the selected search area without fitting the map to all pins, and leaves saved cost settings unchanged. Invalid or unsupported links show a warning and the default search. Links can be copied from the dialog or bookmarked after opening.

## Loaded page references

Listing requests also carry optional `listingFilters.page` metadata, validated separately from the 19 editable values. It captures the loaded page's status, offset, total, all 20 row identities with address/BBL/zoning/price references, and any open inspector selection. Loading retains the previously rendered cards; failed pages carry no rows. Zero and unknown prices remain distinct.

The queued request preserves this metadata independently of the question's 3,000-character limit. It participates in request identity, survives restart, is saved on the user message and is included in subsequent research history. Research receives explicit captured ordering and overall positions; property facts still require verification. Saved messages expose the ordered references in a keyboard-operable disclosure, including their original range even when the current results page changes.

## Listing inspection recovery

Loading details exposes Back to results; failed reads also expose Try again. The requested listing ID stays separate from the successfully loaded selection, so cost previews refresh the correct target while pending or failed details cannot retain an older property reference. Back preserves the loaded search and invalidates later detail publications. Retry uses the same target with the current applied costs. Responses move focus only while the reader remains in the inspector; Back restores the originating card or the map control when that card is outside the page.
