# Arosa NYC research service

Arosa is protected by Sign in with Arosa. The app verifies the Cloudflare Access JWT and derives a private account namespace from the verified Arosa email, with explicit links preserving existing history. It supplies that namespace to the private research service; browser-provided account headers cannot choose another account. The browser receives answers, source excerpts and safe run events, never model or Composio credentials.

The frontend creates a conversation with `POST /api/conversations`, then submits questions to `POST /api/conversations/:id/runs`. `GET /api/runs/:id/events` streams persisted events and resumes from the last event ID after a disconnect. The run endpoints also support steering and interruption. Conversation retrieval and search are account-scoped. The obsolete public `/api/chat` endpoint returns HTTP 410 with a reload instruction, so older clients cannot bypass durable storage or request limits.

## Harness and research

Each research request starts a real Codex App Server on an authenticated loopback WebSocket. Codex chooses its tool calls; there is no fixed extraction/search/answer sequence. The client uses `initialize`, external ChatGPT token login, `thread/start`, native skill input and `turn/start`, and handles `item/tool/call` requests. Only the final completed agent message becomes the answer.

`MODELING_RESEARCH_ENGINE` in the service config picks the model for Modeling runs at start: `codex` (the default, above) or `meta`. In this public release, `RESEARCH_ENGINE=meta` selects Meta for direct research and both workflows; `UNDERWRITING_RESEARCH_ENGINE` and `MODELING_RESEARCH_ENGINE` independently override it. The compatibility default remains Codex when these settings are absent. The supplied `config.example.json` selects Meta for all three. The Meta engine (`meta.mjs`) runs the same registered tools, prompt context, follow-up turns, controls and run events on Meta's Model API through the Responses protocol (`https://api.meta.ai/v1/responses`, streamed with locally replayed encrypted reasoning and tool results). It needs `MODEL_API_KEY` (Secret Manager `acres-meta-model-api-key`, required by the secrets puller while the engine is `meta`); `META_MODEL` overrides the default `muse-spark-1.3` with one of `muse-spark-1.1`, `muse-spark-1.2`, `muse-spark-1.2-contributor`, `muse-spark-1.3`, `muse-spark-1.3-contributor`, or `muse-wonder-1.0`. Muse Wonder Full is a Muse Code subscription capability, not a Model API model, so startup rejects it and every unsupported model before dispatch. The skill index goes in the first request as text. Usage is metered and recorded under the `meta` provider (`meta_research`, `meta_lane_*`) with the configured model in lifecycle and usage evidence, so billing needs a `meta` rate before it is ready. A failed Meta call fails the run; it never falls back to Codex.

The native creative-zoning skill is a slim index (coverage tiers, evidence standards, project-state handling) over a loadable skill library in `acres-research/skills/` (case law, entitlement paths, massing and plans, market and pro forma, non-NYC research). The instructions guide judgment rather than prescribe a workflow. Instruction knowledge is layered (see the repository `AGENTS.md`): `instructions.mjs` holds only operating principles and safety invariants shared by the lead agent, lanes and the legacy judge; skills hold reusable research methods; the capability registry (`capabilities.mjs`) is the single source for which tools and skills exist, their tags and exposure; tools own deterministic calculation and data access; changing facts live in the knowledge corpus, source registry and curated tables with provenance. Lessons are placed by half-life, never tuned to one property or test case. NYC GeoSearch supplies address candidates; PLUTO supplies live parcel records. A separate subject-selection tool prevents a comparison lookup from replacing the main property.

Composio discovery returns relevant tool schemas on demand. The service runs in the Composio project `Acres` with a project-scoped API key limited to tool reads, session management and session tool execution. It creates one tool-router session per signed-in account (user ID is the account namespace, read-only tools only, Instant enabled, connection management and workbench disabled) and one shared service session (user ID `acres-service`) that owns the Exa connection and exposes only search, content retrieval and similar-page discovery. Session IDs persist in `composio.sqlite` beside the chat database, so Composio logs attribute every call to the Arosa account that made it. The server also checks tool metadata and permits only the pinned Exa tools or read-only no-auth/Instant tools discovered during that request. Private mail, team records, messages and account management are unavailable.

## Capability discovery and parallel work

The default (lead) mode is one agent. Core evidence and property tools are direct. When the run is about New York City (the question, the confirmed subject BBL or the latest user turn that names a place), the NYC public records, development ledger, zoning envelope and entitlement scenarios are direct too, because most NYC runs need them; elsewhere they stay behind the gateway so other cities do not carry their definitions on every turn. Other specialist tools (massing, test-fit plans, market, unit mix, pro forma, program comparison, nearby places) and library skills are discovered at run time with `acres_search_capabilities`, executed with `acres_execute_capability`, and loaded with `acres_load_skill`, so the lead thread starts with a small tool surface and pulls in exactly what the question needs. `acres_search_capabilities` only offers tools this host actually built (curated zoning, planning sidecar and Places stay flag-gated).

Parallel work is the lead agent's choice, not a pipeline. `acres_spawn_lanes` runs 1 to 4 lanes from charters the lead writes, with tool sets derived from registry tags (or exact names), all sharing the run's server-assigned citation pool. Lanes return cited drafts with decision-changers and gaps; the lead verifies them and writes the final answer itself, keeping its history and context. At most one spawn call per run; lanes cannot spawn lanes; `RESEARCH_SPAWN_ENABLED: false` removes the tool.

### Legacy lanes mode and fan-out

`RESEARCH_MODE: "lanes"` restores the earlier fixed pipeline for evaluation only. It is never the default, and the historical `RESEARCH_PARALLEL_ENABLED` flag no longer selects it.

- **Tier 1, discovery fan-out** (`acres_fanout_search`): one query runs in parallel across saved knowledge, Serper/Google (direct REST when `SERPER_API_KEY` is set), Exa via the existing Composio service session, and DeepSeek Search (direct REST when `DEEPSEEK_API_KEY` is set). Every query goes to every configured provider. Results merge by canonical URL with reciprocal-rank fusion plus an official-domain prior. Snippets are discovery hints and are never recorded as citable sources. `acres_fetch_url` then reads one chosen URL in full: Cloudflare Browser Run `/markdown` when `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` (permission `Browser Run - Edit`) are set, otherwise a direct fetch through the knowledge HTML/PDF extractor. Only fetched text receives a citation ID.
- **Legacy Tier 2, fixed parallel lanes** (`RESEARCH_MODE: "lanes"`): three Codex children run concurrently by job (parcel and zoning text; cases and administrative decisions; comparables, context, and market), each with tag-derived tools from the registry, all writing into one shared server-assigned citation pool. A failed lane degrades the answer with an explicit gap instead of failing the run. Orchestration is in the research service, not Codex multi-agent, which stays disabled inside every child.
- **Legacy agentic judge** (lanes mode only): a fourth Codex call receives the lane drafts plus the pooled evidence excerpts. It verifies every claim against those excerpts, may run at most one targeted repair round with its own search/fetch tools, then writes the final answer. The existing citation validation still rejects any ID outside the shared pool. Run events add `lane.started/completed/failed` (with `spawned: true` for lead-spawned lanes) and, in legacy mode, `judge.started/completed`.

Spawned lanes multiply Codex usage only when the lead judges parallel work worthwhile (metered `codex_lane_*`, falling back to the `codex` rate; lanes up to three minutes inside a ten-minute lead deadline). Legacy lanes mode always spends four agent calls per run, which is why it is eval-only.

Instant calls use the configured Composio wallet. Firecrawl Instant has retrieved official NYC zoning content through the signed-in Arosa chat, with successful discovery and execution events and a saved source citation. Exa and Composio's public URL-content tool have also returned real content. Provider errors and exhausted credits are returned to Codex so it can use another tool or explain the gap; a successful Instant call does not establish the balance of a separate connected Firecrawl account.

### DeepSeek scope note (D2, option B guardrails)

- **What leaves:** each `acres_fanout_search` call POSTs `{query, count}` to `https://api.deepseek.com/v1/tools/search`. `query` is the raw agent-composed search string; it can contain street addresses, BBLs, and zoning terms. No account ID, user name, conversation, or document text is sent. Only `{url, title, snippet, publishedDate}` is kept from the response.
- **Storage/retention:** queries are processed by DeepSeek (PRC storage under Chinese law per the #178/#179 research); vendor retention duration is **unknown** — treat every sent query as retained indefinitely. Do not put secrets or personal data in fan-out queries.
- **Kill-switch:** set `DEEPSEEK_ENABLED` to `false` (in `/etc/acres-research/secrets.json` or the service env) and restart the research service. The DeepSeek leg is then never constructed and no request reaches `api.deepseek.com` (proven by `fanout.test.mjs`). Default is enabled when a key is configured.
- **Length guard:** queries longer than 128 characters skip the DeepSeek leg only (surfaced in `failedProviders`); Serper/Exa/knowledge still run.
- **Key locations (names only):** field `DEEPSEEK_API_KEY` in `/etc/acres-research/secrets.json` on the research host; Google Secret Manager secret `acres-deepseek-api-key` in project `hyatus-openclaw`; local `~/.secrets/deepseek.env` (mode 600) on the operator workstation. Rotation procedure: [docs/deepseek-key-rotation.md](../docs/deepseek-key-rotation.md).

Source IDs are assigned by the server to retrieved HTTPS documents and explicitly labeled search excerpts. The server rejects fabricated citation IDs. Search results do not prove a complete opinion, operative provision or valid entitlement. There is no dedicated CourtListener/Judyrecords API, exhaustive docket or legal citator integration.

## Isolation and lifetime

The MVP uses the current server OAuth profile through OpenClaw's credential resolver, including token-refresh requests. OpenClaw does not orchestrate MVP inference turns. This bridge and the installed Codex/ws packages are runtime dependencies; the separate builder still runs OpenClaw. Dedicated subscription ownership is not established by a successful inference call.

Each child gets an empty temporary HOME/CODEX_HOME, a temporary workspace, read-only sandbox and only the provided public-research tools. Native shell, unified execution, patching, apps, code mode and native web search are disabled. The loopback listener requires a random capability token kept in a 0600 file, never a CLI argument. The child does not inherit provider, Composio, Google or builder environment credentials. Unexpected server requests fail closed. The child is terminated and its temporary state removed after completion or timeout.

This is a private pilot on a shared VM, not an OS-level tenant isolation boundary. The host broker runs as `openclaw`; tool restrictions and the private HTTP token protect the application boundary. The MVP and builder use separate application workflows, but share this trusted host and Unix identity.

## Conversation storage and recovery

Conversations, messages, queued requests and diagnostic events persist in `/home/openclaw/.openclaw/acres-state/chat.sqlite`, using SQLite WAL mode. The directory is private (0700), and the database, WAL and shared-memory files are 0600. History and search are available across browsers signed into the same Arosa account. Browser storage holds the current conversation selection and draft; it is not the source of truth for saved messages.

Each conversation is attached to a project whose state lives in the same database (`projects`, `project_fields`, served at `/projects/:id/state`): the selected property, nearby places and modeled concepts, each with provenance (producing tool, run and the sources with retrieval dates) and a staleness flag set when an upstream field changes. See [the project state design](../docs/project-state.md).

Modeling (`/modeling`) and Underwriting (`/sites`) are independent workflows. `POST /projects` with `{workflow:"modeling",address,title?}` creates an addressed modeling project without starting research, pricing or an underwriting. The address is required; a project name is optional. `modeling_projects` identifies these projects so parcel matching and site convergence cannot merge them into an underwriting for the same address. Removing a conversation keeps its modeling project and saved work. Existing plan links remain readable in Modeling.

`GET /projects?modelsOnly=true` lists visible modeling projects and existing saved architecture; `sitesOnly=true` excludes independent modeling projects. Both use the existing access checks, search and continuation cursors. Modeling can draw, upload and render before financial work exists. Underwriting controls request zoning and financial outputs without creating or waiting for drawings or 3D models.

Each request starts a fresh harness thread with bounded recent conversation history, the selected property and a summary of the project state. Native Codex thread state is not resumed across requests. The broker runs at most two research jobs concurrently and serializes jobs within a conversation. At service startup, it marks previously running jobs failed with an explicit retry message, then resumes queued jobs. It does not automatically repeat an interrupted model call.

Run events include tool activity, streaming answer updates, controls, completion and failures. Credential fields and recognizable tokens are redacted; private model reasoning is excluded. Completed activity can be expanded in the UI to retrieve its request reference. Account authorization applies to both run results and event replay. The Arosa web API also assigns transport request IDs for its structured error logs. Historical traces created before durable runs remain separate private JSONL files.

The VM boot disk uses the `acres-daily-backup` GCP snapshot schedule with seven-day retention and a 07:00 UTC start within a four-hour execution window. These are crash-consistent snapshots, including runtime configuration. The baseline `acres-verified-baseline-20261011` was restored onto a temporary read-only disk; a copied database passed SQLite integrity checks and contained a known completed request. The temporary disk was removed. The first scheduled snapshot has not yet been verified. Backup retention is separate from application data retention, which currently has no automatic purge.

## Deployment

- Project: Arosa (`hyatus-openclaw`); web container `arosa-acres` on the dedicated VM.
- VM: `openclaw-builder`, `us-central1-a`; service `acres-research`.
- Private HTTP listener: `10.42.0.2:18800`, held by `acres-research.socket` and handed to each process; only the app's network tag can reach it. `GET /healthz` (no token) reports the installed `release`, `draining` and the `active` runs and plan jobs.
- Source modules and skill: `/opt/acres-research/`. Releases are staged in `/var/lib/acres-research-release/next` and installed by `acres-research-apply` before each start; the files the last release replaced are in `/var/lib/acres-research-release/previous`.
- Private configuration: `/etc/acres-research/secrets.json`, root:docker 0640 on the current host.
- Configuration keys: `RESEARCH_TOKEN`, `COMPOSIO_API_KEY` (the `Acres` project key), `CODEX_BIN`. Optional research-loop keys: `RESEARCH_MODE` (`"lead"` default; `"lanes"` restores the legacy fixed pipeline for evals only), `RESEARCH_SPAWN_ENABLED` (boolean `false` removes `acres_spawn_lanes`; default enabled), `RESEARCH_PARALLEL_ENABLED` (historical, no longer selects a mode), `SERPER_API_KEY`, `DEEPSEEK_API_KEY`, `DEEPSEEK_ENABLED` (boolean/`"false"` disables the DeepSeek fan-out leg entirely; default enabled), `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`. Optional `GOOGLE_MAPS_API_KEY` (a key restricted to the Places API (New) and the Street View Static API) enables `acres_nearby_places` and the Street View photo on concept models; `GOOGLE_MAPS_DAILY_CAPS` overrides the per-SKU daily call caps (`places_nearby`, `streetview_metadata`, `streetview_static`, defaults 200, 600 and 400), and the key should also carry quota limits in Google Cloud. The older `COMPOSIO_USER_API_KEY`, `COMPOSIO_ORG_ID`, `COMPOSIO_PROJECT_ID` and fixed session IDs may remain for rollback; the service no longer reads them.

Merge tested code to `main`, then run `./scripts/deploy-research.sh` from your own checkout. The builder host holds no GitHub credential: the script fetches `main` locally, sends the commits the host checkout lacks as a git bundle over IAP SSH, fast-forwards that checkout and requests the install there. The fixed host installer, maintained in `infra/acres-deploy-research`, stages its explicit module and skill list, then restarts the service with no downtime:

- It waits up to 10 minutes for a moment with no active runs or plan jobs, so the handover usually takes about a second.
- The old process drains: it keeps serving every request, including steering and stopping its runs, lets in-flight runs finish on their own deadline (up to 15 minutes, `TimeoutStopSec`) and leaves runs requested meanwhile queued for the next process. Responses close their connections, and once the active work is done it stops listening, finishes the requests it has and closes event feeds, which reconnect from their last event.
- Connections made while one process hands over to the next wait in the socket's backlog instead of being refused. The next process starts once the old one has exited, after `acres-research-apply` installs the staged files, so a draining run never loads files from the next release.
- The installer waits for `/healthz` to report the new release. If it does not, it reinstalls the replaced files, restarts and reports `Rolled back <commit>`.

Only one research process ever has the stores open: SQLite stays single-writer, and startup recovery (which fails runs left `running`) only ever sees runs of a process that has exited. A deploy can take up to 25 minutes to report on a busy service. `./scripts/deploy-research.sh --urgent` skips both waits and stops active runs; use it only when production is broken. `systemctl restart acres-research` (and `acres-server restart research`) drains the same way. Stopping the service alone does not keep research down, because the socket starts it on the next connection: stop `acres-research.socket` as well. To roll back by hand, `sudo mv /var/lib/acres-research-release/previous /var/lib/acres-research-release/next && sudo systemctl restart acres-research`. Restarting `acres-secrets.service` no longer restarts research, which reads `secrets.json` at start and `knowledge.json` on each use. Verify the installed file list before deployment, particularly when knowledge-source work is being developed separately. Install an updated host installer administratively when its file list changes. Deploy UI changes with `app-starter/deploy.sh` and verify the signed-in live browser.

The NYC listings on home read the deal store (`market.sqlite`). Every signed-in account can read it, and admins can sync it, only while `ACRES_DEAL_STORE_ENABLED=true` is set by a systemd drop-in on both `acres-research.service` and `acres-market.service`. `acres-market.timer` refreshes it every six hours once the admin sync configuration has automatic syncing on; each run scrapes each borough separately so every borough gets its full per-type limit.

## Bounds and verification

The experimental curated zoning-envelope tool remains off unless the host configuration sets `ENABLE_CURATED_ZONING` to the boolean `true`. Its recalled rules table requires separate source/applicability review before activation. Ordinary parcel research, cited source retrieval and schematic massing do not require it. Browser input cannot enable the tool.

Each run has one tool budget split by purpose (`BUDGET` in `tools.mjs`): 12 fetch and search calls, 9 records calls, 12 compute calls and 3 reserved calls that unlock only when the deliverable check finds gaps, so at most 36 budget-charged calls per run. The compute set is derived from the capability registry's `cost` tags in `capabilities.mjs`. Tools tagged `compute` (zoning envelope, entitlement scenarios, unit mix, pro forma, program comparison and the floor-plan audit) are in-process arithmetic with no network call, subprocess or provider charge; a test runs every one of them with the network disabled and holds each under a second, and it fails if a newly tagged tool is not exercised. Tools tagged `engine` draw a design concept and also charge the compute cap, so design never trades off against records: the massing concept reads building footprints and Street View once per property, and test-fit plans run the planning engine, which can take up to 120 seconds a call. Every other specialist tool is a records call: NYC public records, the development ledger, municipal parcel records, market inputs, nearby places, site assembly (MapPLUTO polygons and a 60 second engine), market comps (a live HomeHarvest pull), the deal store (which can sync listings on demand), plan saves and the deck. Saved-knowledge search and reads count as fetch calls; a fetch served from cached saved-knowledge text, capability search, skill loads, generated interface and the subject brief are not charged. A re-read of a page already fetched in the run (another `find`, offset or `#fragment` of the same URL) is served from memory and is not charged, up to `FREE_REREADS` (4) successful re-reads per run and only while fetch budget remains; a re-read that fails keeps its slot. Failed tool calls record whether they spent budget (`charged`), so trace reports count only real charges. When records or fetching run out, the refusal states how many compute calls remain and names the tools that size an option (the registry's `sizes` flag: zoning envelope, entitlement scenarios, unit mix, pro forma and program comparison), limited to the tools the agent was offered on this host and in its lane. After the answer validates, a low-effort check turn compares it with the question's asks; if deliverables are missing, the model gets the reserve and one fill turn at the original effort. Set `ENABLE_DELIVERABLE_CHECK` to the boolean `false` to skip it.

The optional private `/mcp-api/tools/` boundary serves the six reviewed operations in [the MCP pilot](../acres-mcp/README.md). It requires a separate `MCP_SERVICE_TOKEN`; the existing web bearer cannot access it, and the MCP bearer cannot retrieve web conversations or runs. Source snapshots and persisted quotas use a separate `mcp-evidence.sqlite` on the host disk. Public corpus release is explicit (`MCP_RELEASED_SOURCE_IDS`); Exa search is disabled unless `MCP_ENABLE_EXA_SEARCH` is deliberately enabled. No MCP tool starts the Codex worker or exposes provider discovery, refresh or deployment. Install the updated host module list before deploying this optional boundary.

The durable service allows two concurrent requests, up to 24 core research tool calls per agent child, five minutes per ordinary harness request, and ten minutes for a lead request that may spawn lanes (lanes up to three minutes each, inside the lead deadline). Exa search defaults to captured text and at most eight results. Nearby parcels are centroid candidates within a bounded box, limited to 50 records, with truncation disclosed. The 30 requests/hour limit is per signed-in identity in the shared database, with at most ten queued requests per conversation. It is not a global billing cap.

Run `npm run check` and `npm test`. Live acceptance must additionally exercise shorthand and ambiguous addresses, a follow-up, actual tool execution and source retrieval, creative/precedent research, private-tool denial, browser citation dialogs, and child cleanup. Unit tests and an HTTP 200 alone are not readiness evidence.

## Market inputs and pro forma

`market.mjs` and `proforma.mjs` are the data and calculation parts of roadmap skills 5 and 9. `createMarketTools({emit, record})` exposes `acres_market_inputs`, which records the submarket's residential rents (USD per net sq ft per month) and condo sale prices (USD per sq ft) by bedroom count, commercial rents (USD per sq ft per year) by use, existing supply with vacancy, the pipeline and monthly absorption. Every figure carries `source` and `retrievedAt`; a figure with a public `url` is recorded as a `market` evidence source so the answer can cite it. The tool validates shape and NYC-plausible ranges (an annual rent passed as monthly is rejected) and never estimates a missing figure. `acres_unit_mix` turns a residential gross floor area into whole unit counts by studio, one, two and three bedrooms using mix percentages, target net unit sizes and an efficiency; omitted values fall back to the stated planning baselines and come back as assumptions. Recording replaces the previous inputs for the answer; `tools.market` is the latest recorded set.

`createProFormaTools({emit, getMarket})` exposes `acres_pro_forma`, a pure calculation over the program (units by bedroom count with net area, commercial area, gross building area), the recorded or passed market inputs, land price, hard and soft cost per gross sq ft, financing (loan to cost, rate, months of interest-only carry) and operating assumptions. Carry is simple interest on a loan drawn for land at closing and evenly for construction, funded from an interest reserve added to the loan. Rentals report GPR, vacancy, operating expenses, NOI, yield on cost, value at the cap rate, development spread, profit, unlevered return on cost, levered return on equity, equity multiple, debt service coverage and cash on cash; condos report sellout, selling costs, net sellout and margins, with any commercial space capitalized. One-way sensitivity tables vary rent, hard and soft cost, cap rate and an entitlement floor-area multiplier against a fixed land price. Each result echoes its normalized inputs, lists the market sources used and includes derivation strings with the numbers plugged in. Both tools are pure code with no external calls; `market.test.mjs` and `proforma.test.mjs` carry the hand-checked worked examples.

## Computed zoning envelope

`acres-research/envelope.mjs` turns the curated bulk rules in `zoning-rules.json` (its `bulk` section and each district's `bulk` pointers) into geometry: per-storey footprint polygons with heights, in feet with x along the front street and z into the lot. `computeEnvelope` takes the lot outline, the streets it fronts (side, width, Special Lower Manhattan District street wall type), the curated district and the special districts, and returns the storeys, the controls that produced them (street wall and base heights, setbacks or sky exposure plane, tower coverage, yards), the lot coverage, the dwelling unit count, the parking requirement and caps, a list of checks to resolve, and the Zoning Resolution section behind every figure. `conceptArguments` shapes the result for `acres_model_concept`, and `acres_zoning_envelope` returns it as `envelope` with `envelope.concept` ready to pass through.

Regimes: the Special Lower Manhattan District (ZR 91-31 to 91-34: base height from street type or 85 ft and 1.5 times the street width, setback depth by lot area, 65/50 percent coverage or 75/60 in the Historic and Commercial Core, 175 ft dimension above 300 ft); commercial districts outside it (ZR 33-432 sky exposure plane, ZR 33-451 and 33-454 towers); residential equivalents (ZR 23-432 base heights, 23-433 setbacks, 23-362 coverage, 23-342 rear yards, 23-435 towers); and manufacturing districts (ZR 43-43). Dwelling units follow ZR 23-52 (no factor in the Manhattan Core and Downtown Brooklyn, 680 elsewhere); parking follows the Manhattan Core rules of ZR 13-10 to 13-12 and is null elsewhere. PLUTO carries no street widths or street wall types, so those are inputs; when missing, narrow-street rules apply and the output says so. The curated figures were read from the current Zoning Resolution text in October 2026 and remain starting points to verify, never a determination.

## Listing investigations

The listing inspector's **Investigate listing** action runs acquisition research with Standard (`deep-research-preview-04-2026`) selected by default and Max (`deep-research-max-preview-04-2026`) available explicitly. Each depth has explicit budgets in `DEPTH_POLICY` (`listing-investigation-prompt.mjs`): Max doubles the public-record rows per query and the cited web pages read before publication (48 instead of 24, with longer excerpts and a 120-second instead of 60-second retrieval budget), adds an audit round, and allows a 90-minute instead of 45-minute deadline and 2,500 instead of 1,500 words. Each objective in `OBJECTIVE_POLICY` (acquisition screening, redevelopment, rental hold, renovation/resale, assemblage) adds its own required memo section and audit checklist, weights the public-record rows, and reads cited pages that match its focus first. An optional question adds a required "Answer to your question" section. The backend hydrates the exact listing and fetches public NYC records before dispatch; browser-provided facts are not used. Results remain account-scoped and attached to the listing, and do not automatically update underwriting or property facts. Before final reconciliation, the depth's cited web sources are read through the existing public HTTPS/DNS-pinned fetcher, with four concurrent requests and bounded text excerpts. Unread sources stay explicitly unavailable and cannot be cited in the published memo. A final Gemini 3.1 Pro evidence-reconciliation step compares the research draft with these source excerpts, the exact supplied records and query coverage before publication. A separate critical-claim audit checks every section against the source evidence, the objective checklist and whether the question is answered, permits exact correction passes within the depth's audit rounds and requires a passing recheck before publication. The memo contract is also checked in code on every round and again at publication: required sections present, in order and not empty, the question section addressing the question (a word sharing a question term's stem or its acquisition topic counts), every ledger and contact table row citing its source unless it marks the point unresolved, the depth's word limit, and web citations only to retrieved pages. Raw research, correction notes, source-check metadata and separate review/audit usage remain saved; unresolved claims, references or omitted supplied property records fail closed. Reconnecting retains the same deep-research interaction and retries only the unfinished review when research is already complete. This is not independent legal or title verification.

Set `LISTING_RESEARCH_ENABLED` to boolean `true` in the research host configuration and provide `GEMINI_RESEARCH_API_KEY`. The normal secret-pull workflow reads `acres-gemini-research-api-key` only when the feature is enabled; provision that Gemini API-restricted key in Google Secret Manager and grant the existing VM identity access to that exact secret before enabling it. Do not put the key in browser configuration or a tracked file. With billing enabled, each depth also requires a validated `BILLING_RATES.listing_research_standard` or `listing_research_max` fixed-call policy. The UI displays the configured charge and reservation before start; no new price is supplied by this feature. Without the required configuration, starting a paid run fails closed.

`listing-investigations.mjs` persists jobs, selected input, prompt version/hash, provider interaction ID, raw response, source annotations and usage in separate SQLite tables. It allows one unresolved investigation per account, two executing jobs per service, ten starts per account per day and the depth's execution deadline. Closing the panel leaves research running; Stop requests provider cancellation. Service shutdown closes local streams, and startup reconnects to saved remote IDs. Ambiguous creation or billing dispatch requires reconciliation and cannot create a replacement automatically; such a job fails at its deadline on its own, leaving any billing hold pending for reconciliation. A Stop the provider refuses because its interaction is gone or already finished closes the job here. A progress connection can reconnect to its existing provider interaction through the saved report panel.

The API is `/listing-investigations`: GET lists the account's reports for `listingId`, POST starts an explicit request with a UUID, GET `/policy` exposes availability, and `/:id` provides status, resumable `/events`, POST `/cancel` and POST `/resume`. The web app proxies these paths under `/api` using the verified account identity. Reports render a restricted Markdown subset as DOM text, never provider HTML, scripts or images. Citation links are HTTPS-only. A completed provider report is marked as requiring source review; it is not promoted to verified project facts.

The host installer includes the three new research modules.

The deadline also schedules a cancellation attempt for an interrupted job with a known provider ID. A failed cancellation is shown as needing attention; it is not reported as a confirmed stop. Citation ranges are decoded as UTF-8 byte offsets, as specified by the Interactions API.

The acquisition-v3 prompt distinguishes historical instruments from current debt, inventory fields from occupancy/legal clearance, and screening capacity from entitlements. Findings drawn from the supplied public-record packet use `[R1]` references, which resolve to that packet's exact official URLs alongside the provider's web citations. These citations identify evidence; they do not automatically validate the model's interpretation.
